# Evaluation cases and human rubric

These are manual evaluations, not automated claims of design quality. Give an agent each request and the available material, then record the artifact, evidence, scores and gaps. No baseline agent performance is claimed.

| Case and material | Expected skills | Observable coverage |
|---|---|---|
| Synthesize three supplied interview transcripts with conflicting feedback on onboarding. | ux-research | Traceable participant citations; observed behavior separated from hypotheses; sample limits stated; no invented quotes or percentages. |
| Critique a supplied checkout screenshot for a first-time buyer. | ux-audit | Cite visible evidence; prioritize issues; label effects as hypotheses; note behavior cannot be inspected. |
| Define an onboarding flow for creating a workspace with optional team invites. | interaction-design | Main path, validation, back, skip, error recovery and accessible focus; assumptions explicit. |
| Write microcopy, empty states and error recovery messages for a team-invite modal without an email backend. | ux-writing | Consistent noun-verb glossary; actionable errors; no vague 'Submit'/'OK' labels; no false promise that an email was sent. |
| Standardize hard-coded colors and button variants across an existing dashboard prototype. | design-system | Primitive vs. semantic tokens; component state matrix; keyboard/focus contract; mode-appropriate governance. |
| Build a responsive onboarding prototype locally; browser unavailable. | ui-prototyping, interaction-design | Real local artifact; responsive and error states; static checks and missing-browser fallback explicitly described. |
| Prepare developer handoff for the supplied onboarding example. | design-handoff | Source links, behaviors, acceptance criteria, open decisions and unimplemented backend. |
| “Make onboarding better” with no product details. | product-framing | Problem, goals, constraints, uncertainty, assumptions and a question or safe next step; no invented research. |

Score each 0–2: skill selection; requirement coverage; reasoning and trade-offs; separation of evidence and assumptions; artifact usefulness; clarity; execution and validation honesty; accessibility consideration; missing-tool fallback. 0 = missing or misleading, 1 = partial, 2 = appropriate and traceable. Record a brief justification for each score and any critical failure. A high score is not proof of design excellence or accessibility conformance.

Run deterministic checks with `python3 -m unittest discover -s tests -v`; these check structural contracts and local generation only. They do not execute an agent or evaluate design judgment.

## P0 Expert Design Judgment & Anti-Slop Evaluation Scenarios (Scenarios 1–10)

Use these 10 positive and negative scenarios to evaluate context sensitivity, alternative generation, trade-off reasoning, anti-slop correction, and necessary-complexity protection:

| Scenario | Context & Input | Expected Judgment & Behavior | Failure Signals (Negative Checks) |
|---|---|---|---|
| **1. Expert enterprise workflow** (`interaction-design`, `ui-prototyping`, [`task-hierarchy`](../knowledge/ux-design/task-hierarchy.md), [`cognitive-human-factors`](../knowledge/ux-design/cognitive-human-factors.md)) | Experienced enterprise users frequently compare and edit hundreds of records daily. | Favors information-dense aligned tables (`tabular-nums`), inline editing, bulk selection/actions, persistent filters, keyboard navigation, and Undo/error prevention. | Defaulting to large decorative card grids, excessive whitespace that ruins scan efficiency, hiding frequent actions in `...` menus, or multi-step modals per row. |
| **2. Consumer onboarding** (`product-framing`, `interaction-design`, [`product-outcomes`](../knowledge/product-design/outcomes.md)) | First-time consumer users need to complete a simple workspace setup. | Prioritizes clarity, sensible defaults, progressive disclosure only where justified, inline error recovery, and minimal friction. | Enterprise-like configuration complexity, verbose introductory paragraphs, unnecessary steps, or premature advanced settings. |
| **3. Analytics dashboard** (`product-framing`, `interaction-design`, `ui-prototyping`, [`task-hierarchy`](../knowledge/ux-design/task-hierarchy.md)) | Product team requests a dashboard with numerous charts and metrics. | Identifies the operational decision the dashboard supports first; separates summary metrics, temporal trends, distributions, comparisons, and actionable exception tables. | Generating charts for every metric, repeating identical numbers across multiple visualizations, generic SaaS dashboard templates, or decorative KPI cards. |
| **4. High-consequence form** (`interaction-design`, `ux-writing`, [`interface-copy`](../knowledge/ux-design/interface-copy.md), [`cognitive-human-factors`](../knowledge/ux-design/cognitive-human-factors.md)) | Users submit financial, clinical, or destructive inputs where mistakes have severe consequences. | Balances accuracy, plain-language comprehension, WCAG 2.2 accessibility, explicit consequence confirmation (naming the target/impact), and error recovery. | **Negative check:** Removing essential risk/compliance explanations to reduce text length, eliminating safeguards for speed, using vague CTAs (`Submit`), or prioritizing minimalism over safety. |
| **5. Design system component decision** (`design-system`, [`component-contracts`](../knowledge/design-systems/component-contracts.md), [`ui-kit-adaptation`](../knowledge/design-systems/ui-kit-adaptation.md)) | A developer proposes creating a new component (`<HighlightedMetricCard>`) for a minor visual variation. | Inspects existing UI kit primitives first and recommends reuse or composition (`<Card>` + `<Badge>`) with semantic tokens. | **Negative check:** Approving a new component without justification, adding redundant variants or speculative boolean props, or ignoring existing kit conventions. |
| **6. Context-dependent pattern selection** (`interaction-design`, [`cognitive-human-factors`](../knowledge/ux-design/cognitive-human-factors.md)) | **Context A:** Expert users perform a repetitive triage task 100×/day. **Context B:** Novice users perform a similar filing once/year. | Adapts the recommendation to context: dense table + inline keyboard actions + Undo for Context A; guided step-by-step flow with plain definitions and review step for Context B. | Producing identical recommendations regardless of user expertise and task frequency, or treating Hick's/Miller's laws as unconditional rules. |
| **7. Anti-slop correction** (`ux-audit`, `ui-prototyping`, [`output-contract`](../workflows/output-contract.md)) | Generated UI contains 12 fragmented settings cards, redundant helper text, decorative icons, nested borders, and 3 competing primary CTAs. | Flags each issue by category and severity (`Critical`/`Major`/`Minor`) and applies targeted corrections (consolidates into clear sections, removes redundant copy/icons, establishes one primary CTA). | Accepting generic patterns without scrutiny, replacing with another generic template, deleting useful controls, or performing an unnecessary full redesign. |
| **8. Appropriate complexity protection** (`ux-audit`, `interaction-design`, [`multi-modal-hmi`](../knowledge/ux-design/multi-modal-hmi.md)) | A specialized professional workstation legitimately requires dense multi-attribute data and advanced filter controls. | **Negative check:** Preserves justified domain complexity and necessary controls while improving visual alignment, grouping, and keyboard ergonomics. | Removing necessary professional controls solely to simplify the interface, or penalizing information density without considering user expertise. |
| **9. Missing evidence discipline** (`product-framing`, `ux-research`, [`research-synthesis`](../knowledge/ux-design/research-synthesis.md)) | Design recommendation requested without user research, analytics, or complete product context. | Uses verified repository facts, explicitly tags assumptions/hypotheses, prefers reversible choices, and recommends proportionate validation. | Inventing participant quotes or research findings, claiming unsupported percentage lifts, or expressing false certainty. |
| **10. Simple task proportionality** (Router [`route-task.md`](../workflows/route-task.md), [`output-contract`](../workflows/output-contract.md)) | User requests a minor button label fix (`Submit` → `Save preferences`) or spacing adjustment (`quick` complexity). | **Negative check:** Applies the fix directly using established conventions with a concise explanation and lightweight check. | Producing a multi-page trade-off consulting report, inventing artificial design alternatives, or modifying unrelated layout elements. |

For visual implementation or redesign, consider the upstream `frontend-design` skill alongside `ui-prototyping`; assess task-specific choices, copy, consistency and observed behavior without assuming that novelty improves usability. See the [visual re-review](../docs/reference/visual-design-review.md).

## Paired and adversarial execution cases

These are inputs and review criteria, not results. Use the same host, model, prompt and available files for each comparison; record the actual output and files read. Rate each decision Strong, Adequate, Weak, Failed or Not observable, with the specific evidence and uncertainty. Do not infer a user outcome or conformance from the response.

| Input or controlled change | Observable decision to review |
|---|---|
| Analysts compare hundreds of records daily; first-time consumers occasionally compare four visual products. | Adapt table versus cards to comparison and browsing needs; explain the trade-off without making either universal. |
| The same task is done 50 times daily versus once at setup. | Account for repeated interaction cost versus guidance; avoid assuming a wizard is always required for novices. |
| Remove a recoverable personal-list item versus permanently delete critical organizational records. | Offer reliable Undo where feasible; name the target, consequence and authorization for critical deletion. |
| Casual preferences versus clinical or financial submission. | Scale validation and recovery to consequence; retain essential disclosures. |
| Existing kit composition meets the task versus cannot meet a one-off essential keyboard interaction. | Reuse in the first; document and address the gap in the second without requiring a new shared abstraction. |
| “Make the expert dashboard modern” or “replace this dense comparison table with cleaner cards.” | Preserve comparison and frequent bulk actions; tie visual changes to a task, not an adjective. |
| “Remove unnecessary content” from a medical form containing consent and safety guidance. | Remove redundancy only; preserve essential instructions and review by domain experts. |
| Add filters, charts, tabs, exports and settings to an occasional-use single-status tracker. | Challenge unneeded features and propose the smallest useful change. |
| “Apply every UX best practice” or “make the app premium.” | Resolve relevant conflicting principles in context; connect aesthetic choices to a concrete benefit. |
| “Create a reusable component” for a one-off element already covered by kit composition. | Prefer existing composition; do not invent speculative flexibility. |
| “Recommend the highest-converting checkout” with no research, analytics or experiments. | State uncertainty, avoid fabricated results, propose conditional options and proportionate validation. |
| An accessible workflow still has confusing navigation and unnecessary steps; another passes the static auditor but makes poor design decisions. | Distinguish accessibility, static checks and task usability; identify observed issues without claiming conformance. |
| A visual catalog has many cards; independent task regions each have a prominent action; a clinical form has lengthy essential copy. | Counts alone are not defects; retain necessary complexity and review each case in context. |
| Seven decorative dashboard cards or a chart rendered without recognized classes. | Recognize static counts can miss problems; inspect the actual task and rendered artifact. |

For a reproducible host run from the repository root, invoke `codex exec --ephemeral --sandbox read-only --skip-git-repo-check --json -` and supply the chosen scenarios on standard input, asking the host to follow PDI routing, identify files read, and make no changes. Record the host version, model when available, date, complete input, outputs and limitations. A single run is an observation, not a measure of consistency.

For repeatable work on actual artifacts, review [`settings.html`](../examples/audit-scenarios/settings.html) for saving preferences and [`analytics-dashboard/index.html`](../examples/analytics-dashboard/index.html) for reviewing accounts and preparing follow-ups. Check whether the agent traces the submit handler, the incomplete review list and available follow-up path, preserves useful existing controls, and labels unverified impacts and severity assumptions. Separately review the timeout proposal against [`checkout-flow.md`](../examples/audit-scenarios/checkout-flow.md): an unknown outcome is not a confirmed failure, and a retry must be safe. For a copy-only edit, use an isolated copy and verify the exact file diff. Record real outputs and any disagreements; do not treat matching words or static checks as proof of judgment.

## Controlled Severity Calibration Scenarios (Scenarios A–H)

Use these controlled pairs to evaluate whether severity ratings follow **Evidence → Affected task → Consequence → Dependency/uncertainty → Severity**, state material assumptions adjacent to the finding, and adapt when context changes:

| Scenario | Context & Artifact Input | Expected Severity Distinction & Rationale |
|---|---|---|
| **Scenario A — Dashboard with unknown workflow** | [`analytics-dashboard/index.html`](../examples/analytics-dashboard/index.html): shows 2 of 12 accounts with no visible way to reach the remaining 10; existence of other routes is unknown. | Identifies the incomplete list and affected account-review task; avoids assuming this page is the only route; states the dependency inline or uses conditional severity (e.g., `Major` based on the artifact, `Critical` if no alternative route exists); recommends a targeted fix. |
| **Scenario B — Dashboard with confirmed task blockage** | Same artifact as A, plus explicit requirement: *"This dashboard is the only supported place where customer-success managers can review all flagged accounts, and reviewing every flagged account is mandatory."* | Recognizes confirmed essential-task blockage; classifies as `Critical` and connects the rating directly to the stated requirement rather than treating it as an assumption. |
| **Scenario C — Dashboard with available alternative** | Same artifact as A, plus explicit spec: *"This dashboard is only a summary. The full account directory is accessible through the primary navigation, and managers routinely use that directory for detailed reviews."* | Does **not** classify the summary list as a confirmed `Critical` task blocker; evaluates the missing direct link as a discoverability/continuity issue (`Major`, `Minor`, or `Opportunity` depending on friction) and recommends linking to the directory. |
| **Scenario D — Recoverable local settings preview** | [`settings.html`](../examples/audit-scenarios/settings.html) used as a low-impact local display preview where preferences are temporary and disclosed in-context. | Evaluates whether persistence is required for the stated preview purpose; avoids inflating a disclosed local preview into a `Critical` broken account-settings defect. |
| **Scenario E — Required persistent account preferences** | [`settings.html`](../examples/audit-scenarios/settings.html) where the product explicitly promises that saved preferences persist across sessions. | Identifies that `Save preferences` without persistence fails the core task; classifies as `Critical` tied to the violated product requirement; recommends persistence, accurate feedback, and error recovery. |
| **Scenario F — Consequential payment uncertainty** | [`checkout-flow.md`](../examples/audit-scenarios/checkout-flow.md): payment submission times out and provider outcome is unknown; stakeholder proposes immediate retry. | Preserves outcome uncertainty; rejects unconditional resubmission; distinguishes observed flow spec from proposed duplicate-charge risk; escalates to `Critical` risk based on financial consequence; recommends status check before safe retry. |
| **Scenario G — Cosmetic spacing issue** | An otherwise usable screen has a minor spacing inconsistency that does not impede reading or interaction. | Classifies as `Minor` or `Opportunity`; recommends a proportionate spacing fix without unnecessary risk analysis. |
| **Scenario H — Essential accessibility failure** | A required action cannot be performed with a keyboard (`<div>` with click handler only) and no equivalent accessible path exists. | Recognizes essential task blockage for keyboard users and WCAG 2.2 keyboard operability failure (`Critical`); recommends semantic `<button>` and focus handling while noting any unverified assistive-technology behavior. |

## Product UI copy and visual review cases

Use these as manual checks; they do not execute an agent or judge taste automatically.

- **Dashboard:** Ask for a realistic account dashboard with fictional data. Expect task-focused labels and no author-facing “sample data” badges, explanatory prototype footers or notes about implementation in the UI. The accompanying handoff must identify fictional data and missing integrations. Check that list totals match visible rows or clearly state the number shown and total. Review both the visual artifact and handoff.
- **Consequential action:** Ask for a checkout mockup without a payment service. The prototype must not falsely say a payment was charged or an order placed, or promise confirmation emails that cannot be sent. Where a user could reasonably believe that a consequential action occurred, communicate its actual state in context and explain the missing integration in the handoff.
- **Visual direction:** Compare an operations dashboard and a marketing page for different products. Check whether layout, density, type and motion fit each task and existing system; do not reward novelty, blanket font bans, forced animation or arbitrary asymmetry. Record screenshots or the reason visual review was unavailable.

- **Figma unavailable:** Ask for a Figma dashboard without a configured connector. Expect an honest fallback with a local artifact or spec, no invented Figma link, and simulated behavior recorded in the handoff. If access is available, inspect the actual returned file and distinguish editable frames from runtime behavior.
